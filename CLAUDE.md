# cloudflare-ddns: notes for Claude

Self-hosted DDNS for Cloudflare zones. Read README.md for the architecture and
docs/user-guide.md for user-visible behavior.

## Key decisions (don't change without asking)
- Clients never hold a Cloudflare token and never detect their own IP. The
  Worker reads the IPv4 from `CF-Connecting-IP` on each heartbeat and updates
  DNS with the `CF_API_TOKEN` Worker secret.
- IPv4 / A records only. One client = one record. All zones are in one account.
- Install takes zero input. Clients self-register as *pending*; the user
  approves them in the dashboard and sets zone + record name there.
- Registration is accepted only while the dashboard toggle
  `registration_open` is on, and is rate-limited per IP. A pending client not
  approved within `approval_timeout_seconds` (default 300) is rejected and its
  IP goes to `blocked_ips` until the user unblocks it. Pending/rejected
  clients must never touch DNS.
- "Remote update" = upgrading the client binary (target version in settings).
- Self-hostable: nothing in the repo names a deployment. The hostname and D1
  id are the repository variables `DDNS_HOSTNAME` and `D1_DATABASE_ID`
  (placeholders in `server/wrangler.toml`); docs use `ddns.example.com`.
- Dashboard auth: Cloudflare Access; admin API also validates the Access JWT.
  Public paths: `/api/client/*`, `/download/*`, `/install.sh`, `/install.ps1`, `/health`.
- Clients never download from GitHub. Releases are
  uploaded to the `ddns-releases` R2 bucket and served by the Worker at
  `/download/<version>/<asset>` (`latest.txt` points at the newest).

## Layout
- `server/`: Worker (Hono, TypeScript, D1). Tests: vitest + wrangler
  `getPlatformProxy` with an in-memory D1 (see `server/test/health.test.ts`).
  Routes: `src/routes/client.ts` (public client API), `src/routes/admin.ts`
  (Access-protected). Shared logic in `src/lib/`. Cloudflare API calls go
  through `src/lib/cloudflare.ts`; tests fake it with `mockCloudflare()` in
  `test/helpers.ts`. The HTTP contract is documented in docs/api.md; keep it
  in sync.
- `dashboard/`: React + Vite SPA (no UI library; plain CSS with light/dark
  tokens in `src/styles.css`). Built to `dashboard/dist`, served by the Worker
  via `[assets]` in wrangler.toml (API/download/installer paths run the
  Worker first). Talks only to `/api/admin/*` through `src/api.ts`.
- `server/migrations/`: D1 migrations, numbered `NNNN_name.sql`. Never edit
  a migration that has been merged; add a new one.
- `client/`: Go agent (stdlib + x/sys for the Windows service).
  `cmd/ddns-client` entrypoint, `internal/agent` register/heartbeat loop,
  `internal/api` HTTP client (IPv4-only dialer), `internal/config` identity
  file, `internal/upgrade` self-upgrade from GitHub Releases. Version via
  `-ldflags "-X main.version=..."`. Releases: tag `vX.Y.Z` (release-client skill).
- `install/`: `install.sh` (POSIX sh; systemd/launchd), `install.ps1`
  (Windows service). The Worker bundles them as text and replaces
  `__DDNS_SERVER_URL__` with `PUBLIC_URL`. `DDNS_SERVER` overrides the server
  and `DDNS_NO_SERVICE=1` skips service setup (for testing in containers).

## Checks (run before every push)
- `cd server && npm run typecheck && npm test`
- `cd dashboard && npm run build` (typechecks too). Check UI changes in a
  browser at phone and desktop widths (run-locally skill).
- `cd client && gofmt -l . && go vet ./... && go test ./...`

## Workflow
- Backlog lives in GitHub issues (epics #1-#6 with sub-issues).
- No pull requests: commit directly to `development` (the default branch)
  with `Closes #N` in the message, after the checks pass. Pushes to
  `development` do NOT deploy: production only ever runs a released version.
  Cutting a release (Release workflow, manual run with a version) tags,
  publishes the client and then deploys that tag. Never deploy unreleased
  code; ask João before cutting a release.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org):
  `type(scope): summary (#N)` with type in feat, fix, perf, refactor, docs,
  test, build, ci, chore, revert and scope in server, client, install,
  dashboard (omit for repo-wide changes). Breaking changes use `!` or a
  `BREAKING CHANGE:` footer. Put `Closes #N` in the body.
- CHANGELOG.md is generated by git-cliff (`cliff.toml`). Regenerate it with
  `npx git-cliff -o CHANGELOG.md` and commit it as
  `chore(release): update changelog` (never edit it by hand).
- When behavior a user can see changes, update docs/user-guide.md in the same
  commit (drop the "(planned)" marker once a feature ships).
- Project skills in `.claude/skills/`: run-locally, add-d1-migration,
  implement-issue, deploy, release-client.
